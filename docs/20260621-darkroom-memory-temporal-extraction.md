# Darkroom 记忆时间信息提取方案

> 生成时间：2026-06-21
> 范围：是否在提取结构化记忆时同时提取时间相关描述

---

## 当前状态

`darkroom_memories` 表当前只有：

- `created_at`：记忆被写入数据库的时间
- `content`：记忆文本
- `keywords`：关键词

这意味着系统知道"这条记忆是什么时候被记录的"，但**不知道记忆内容里描述的是什么时候发生的事**。

例如：

> "去年夏天我和小王一起去过杭州"

当前只保存了内容，没有单独保存"去年夏天"这个时间信息。

---

## 可行性

完全可行，有两种方案。

### 方案 1：轻量版（推荐先上）

在 extraction prompt 里要求 LLM 在生成 `content` 时，把时间信息明确写进文本里。例如：

```json
{
  "content": "2024年夏天，用户和小王一起去了杭州",
  "keywords": ["2024年夏天", "杭州", "小王", "旅行"],
  "confidence": 0.9
}
```

**优点**：

- 不改表结构
- 时间信息进入 `content` 和 `keywords`，语义检索能召回
- AI 读 content 时自然知道时间顺序

**缺点**：

- 时间格式不统一（"去年夏天"、"2024年6月"、"上周三"）
- 不方便做时间排序或状态覆盖的精确判断

### 方案 2：结构化时间字段（后续升级）

给 `darkroom_memories` 增加一个 `time_context` 或 `temporal_tags` 字段：

```json
{
  "content": "用户和小王一起去了杭州",
  "time_context": {
    "description": "2024年夏天",
    "normalized": "2024-06~2024-08",
    "type": "past_specific"
  }
}
```

`type` 可以是：

- `past_specific`：过去具体时间点（去年夏天、2023年）
- `past_vague`：模糊过去（以前、曾经）
- `present`：现在/当前状态
- `future`：未来计划
- `recurring`：经常性（每次、常、总是）

**优点**：

- 可以做时间排序
- 可以做状态覆盖（比如"2023年单身" vs "2025年恋爱中"）
- 关系状态变化更容易追踪

**缺点**：

- 需要改表结构
- LLM 抽取时间可能不准
- 查询逻辑变复杂

---

## 必要性

对于你提到的两个目的，确实有帮助。

### 1. 厘清记忆先后顺序

没有时间的记忆堆在一起，AI 会把所有记忆当成"同时存在的事实"。比如：

- "Aidan 和 Dex 在 Reborn 接吻过"
- "Aidan 说他和 Dex 只是朋友"

如果没有时间，AI 不知道哪个在前、哪个在后，可能会同时引用两条，导致矛盾。

### 2. 状态覆盖

人的状态会变化。比如：

- "小马和勺子正在约会"（2025年）
- "小马和勺子已经分手，现在和锋锋在一起"（2026年）

有时间信息后，AI 可以优先使用更近期的状态，而不是把两条同时当真。

---

## 建议

**先上方案 1 的改良版**：

1. 在 extraction prompt 里明确要求 LLM 把时间信息写进 `content` 开头：
   - 有具体时间 → 写成 "2024年夏天"
   - 是当前状态 → 写成 "目前"
   - 是过去习惯 → 写成 "过去"
   - 是未来计划 → 写成 "计划/将"

2. 同时把时间词放进 `keywords`，比如 `["2024年夏天", "过去", "目前", "计划中"]`

3. 跑一段时间观察提取质量，看时间信息是否稳定、是否对 AI 回答有明显改善

如果效果好的话，再升级到方案 2 的结构化字段。

---

## 风险

时间抽取容易出问题，比如：

- 用户说"去年夏天" → 系统记录为"2024年夏天"，但对话发生在 2026 年，其实是"2025年夏天"
- 用户说"下周" → 需要相对于对话时间解析

所以如果要精确时间，建议存**相对时间描述**（"去年夏天"）而不是 LLM 帮你换算的绝对时间。这样 AI 自己可以根据当前日期理解。
