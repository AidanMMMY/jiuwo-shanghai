# Story Relay 剧情连贯性优化方案

当前故事接力的连贯性主要靠 **prompt 里的上下文注入 + 生成规则约束** 来控制，没有额外的“剧情一致性模型”或记忆检索。

## 当前机制

每次用户提交续写时，`app/api/story-relay/continue/route.ts` 会调用：

```ts
generateStoryContinuation(
  names,             // 从 darkroom memories 提取的人名
  segments.length,   // 当前已有几段
  latestQuestion,    // 上一段结尾的 AI 提问
  userInput,         // 用户这次写的内容 / 选的选项
  authorName         // 用户的名字
);
```

这些变量会被填进 `lib/story-relay-ai.ts` 的 `CONTINUE_PROMPT` 模板里，AI 看到的是：

- 当前故事已有 {n} 段
- 上一段结尾的问题是：{latestQuestion}
- 用户的回答是：{userInput}
- 用户的名字是：{userName}

也就是说，AI 只知道“上一段结尾的问题 + 用户这次回答 + 用户名字”，**看不到完整的故事全文**，所以它主要靠 `latestQuestion` 来推断该往哪走。

### 当前规则约束

- 必须紧接上一段结尾
- 不得擅自切换主角
- 女性角色少出场
- 第三人称、无第一人称
- 长度控制在 150–250 字
- 对话按说话人分段

### 为什么还会断

因为 AI 只看到 **一个问题 + 一个回答**，中间没有真正的“故事记忆”：

- 如果用户回答比较发散，AI 容易顺着用户名字另开一条线。
- 如果上一段结尾的问题本身比较开放，AI 可能选一个“更好写”的方向，而不是真正延续上段结尾的画面。
- 它看不到更早的情节，所以人物状态、关系线可能前后不一致。

## 优化方向

### 1. 把上一段的故事正文也喂给 AI

**实现方式**

`generateStoryContinuation` 里不只传 `latestQuestion`，也把 `latestSegment.storyZh` / `storyEn` 一起放进 prompt。AI 看到：

- 上一段完整正文
- 上一段结尾的问题
- 用户回答
- 用户名字

**优点**

- **上下文更完整**：AI 知道“老王手机屏幕亮了一条未读消息”，不会把主角突然换成 Aidan。
- **人物状态更一致**：上一段里谁在做什么、什么情绪，能直接继承。
- **实现简单**：数据库里已经存了 `storyZh`，只需改 prompt 模板和传参。

**代价/风险**

- **token 变长，成本上升**：每续写一次都要多付上一段正文的长度。故事长了之后会更明显。
- **仍然看不到更早的情节**：只能保证“上一段 → 下一段”连贯，第 5 段和第 1 段的人物关系仍可能脱钩。
- **AI 可能照搬/复述**：如果 prompt 没写好，AI 容易把上一段内容又改头换面写一遍，而不是推进剧情。

**适合场景**

想低成本先把“相邻两段不断线”这个问题解决掉。

---

### 2. 给每段生成剧情摘要，续写时喂最近 3–5 段摘要

**实现方式**

每次生成新段落后，让 AI（或规则）生成一句“剧情摘要”，例如：

> 老王收到匿名消息，Aidan 偷瞄被发现，小马调侃老王。

后续续写时，prompt 里带上最近 N 条摘要 + 上一段完整正文 + 用户回答。

**优点**

- **长程记忆**：AI 能记住 5 段之前的关键事件，人物关系和伏笔不容易丢。
- **token 可控**：摘要比全文短很多，story 长了也不爆炸。
- **方便做“往期章节”**：摘要可以直接用来展示章节梗概。

**代价/风险**

- **需要多一次 AI 调用**：每生成一段后，再调用一次生成摘要，延迟和成本都增加。
- **摘要质量不可控**：如果摘要漏了关键细节，后续剧情会沿着错误方向走。
- **实现复杂度高**：需要新增 `segment_summary_zh/en` 字段，新增 API 逻辑，还要考虑失败回退。

**适合场景**

故事经常写很长（10 段以上），需要保持跨段连贯。

---

### 3. 限制用户输入必须回应上一段的问题

**实现方式**

前端或后端加一个校验：如果 `userInput` 和 `latestQuestion` 明显无关，就拒绝提交并提示“请回应 AI 的问题”。可以用简单规则（关键词匹配）或让 AI 判断相关性。

**优点**

- **强制连贯**：用户不能突然把故事拐到火星，剧情发展方向可控。
- **减少 AI 乱编**：输入越贴近问题，AI 越容易写出合理的续写。
- **体验一致**：每个用户都在回答同一个悬念，故事更像“接力”。

**代价/风险**

- **挫败感**：用户可能想自由发挥，被拦截会觉得 rigid。
- **判断容易出错**：规则太严会误杀；用 AI 判断又增加延迟和成本。
- **失去惊喜**：故事接力的魅力之一是用户把剧情带到 AI 想不到的地方，全限制住就太 scripted。

**适合场景**

当前最大问题是“用户输入和上一段脱节”，想先快速止血。

---

### 4. 用结构化状态表（焦点人物、悬念、人物关系）

**实现方式**

维护一个 JSON 状态对象，每次生成后更新：

```json
{
  "focusCharacter": "老王",
  "openQuestion": "未读消息是谁发的？",
  "mood": "悬疑、轻松",
  "relationships": {
    "Aidan-老王": "互相调侃",
    "Ethan-小刘": "Ethan 捉弄小刘"
  }
}
```

续写 prompt 里把这张表作为系统提示一起给 AI，并要求 AI 生成时也输出更新后的状态表。

**优点**

- **最强的连贯性**：AI 明确知道“现在主线是谁、悬念是什么、人物关系如何”，不容易跑偏。
- **方便人工干预**：你可以在 admin 页面直接改状态表，手动纠正剧情。
- **可做剧情推荐**：根据焦点人物和关系，AI 生成的 suggestions 会更贴合。

**代价/风险**

- **实现最重**：需要新增表/字段、状态解析逻辑、状态更新逻辑、错误回退。
- **AI 可能不遵守**：要求 AI 每次输出状态更新，需要更复杂的 JSON schema，解析失败率上升。
- **灵活性下降**：故事被框在状态表里，意外转折和群像戏会变少。
- **需要 prompt engineering**：状态怎么用、怎么更新，要反复调。

**适合场景**

故事接力长期运营，剧情复杂、人物多，愿意投入开发量。

---

## 对比总览

| 方向 | 开发量 | 连贯性提升 | 灵活性损失 | 成本增加 |
|---|---|---|---|---|
| 只喂上一段正文 | 小 | 中 | 小 | 中 |
| 维护剧情摘要 | 中 | 高 | 小 | 高 |
| 限制用户输入 | 小 | 中 | 高 | 低 |
| 结构化状态表 | 大 | 最高 | 中 | 中 |

## 建议

**先做方向 1（喂上一段正文）**，这是投入产出比最高的；如果后续还出现长程脱线，再考虑方向 2（摘要）或方向 4（状态表）。方向 3 可以作为临时止血，但长期用会太死板。
