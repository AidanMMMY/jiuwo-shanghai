啾喔故事接力：分步实施方案选项

记录日期：2026-06-18

状态：方案讨论稿，待确认后进入详细设计

用途：保存当前思路与迭代方向，供后续查询

已确认的核心需求

  • 故事模式：公共接龙。全站只有一篇正在进行的啾喔故事，任何人都能贡献一段。
  • 测试期入口：秘密路径 + Token，例如 /story-relay?token=jiuwo，暂时不放入主导航。
  • AI 提问形式：混合模式。AI 先问开放性问题，同时在问题下方给出 2 个建议方向。
  • Milestone 展示：桌面端用右侧 contributor 时间线；移动端用行内标签 + 可折叠底部 contributor 墙。
  • 语言策略：双语界面，AI 同时生成中英文两个版本的故事段落。
  • 持久化：复用现有 Neon Postgres，新增故事接力相关表。
  • 重置与归档：需要管理员一键「开启新章」，旧故事归档为历史篇章。
  • 人名来源：动态从 darkroom_memories 抽取 + data/story-relay-seeds.json 手动保底名单。
  • 用户姓名：服务端 session 记录，首次提交后提示「姓名后续很难更改」。

方案 A：最小可用版（推荐）

核心结构

只维护「一篇正在进行的公共故事」+「历史归档篇章」。

当前故事的所有段落存在同一张表 story_relay_segments。当管理员触发重置时，系统把当前故事整体复制到 story_relay_chapters 表，然后清空 story_relay_segments，并重新调用 AI 生成开头。

优点

  • 数据表最少，实现最快。
  • 适合「先测试、暂时不上入口」的节奏。
  • 已经保留了归档能力，未来扩展成章节浏览不困难。

缺点

  • 当前故事只有一篇，无法同时存在多个并行的实验故事。
  • 归档是「复制后清空」，历史章节和当前章节的数据结构略有不同。

关键文件（预估）

  • app/story-relay/page.tsx：故事接力页（测试期带 token 校验）
  • app/api/story-relay/chat/route.ts：AI 续写接口
  • app/api/story-relay/segments/route.ts：提交新段落接口
  • app/api/story-relay/reset/route.ts：管理员重置/归档接口
  • lib/story-relay.ts：数据库操作
  • data/story-relay-seeds.json：保底人名与故事种子

方案 B：一开始就按「章节」设计

核心结构

故事天然分章节，每一章独立成篇。

  • story_relay_chapters：所有章节（包括当前进行中的）
  • story_relay_segments：所有段落，通过 chapter_id 关联
  • 当前进行中的章节 ID 存在 site.json 或单独配置里
  • 用户永远在最新章节上接龙，但前端提供往期章节切换

优点

  • 归档概念更自然，「第 1 章 / 第 2 章」的展示很清晰。
  • 表结构统一，当前章节和历史章节没有差异。
  • 未来可以支持多线故事或限定主题章节。

缺点

  • 表结构和前端路由都要多一层。
  • 测试周期更长，不适合「先快速验证玩法」的阶段。

适用时机

如果方案 A 验证成功、决定长期保留并扩大玩法，再迁移或重构到方案 B。

方案 C：Admin 预审版

核心结构

用户提交后不立刻写入故事，而是进入 story_relay_pending_segments 待审队列。管理员在后台审阅后点击「采纳」，段落才成为正式故事的一部分。

优点

  • 完全可控，不怕有人把故事带偏或提交不合适内容。
  • 适合对品牌调性要求极高、希望人工把关的场景。

缺点

  • 体验不实时，用户提交后看不到立刻生效，失去接龙爽感。
  • 管理员需要经常上线审核，增加运营成本。
  • 与「AI 自动续写」的循环节奏冲突较大。

适用时机

仅在内容风险不可控、或上线后 abuse 严重时才考虑引入。

推荐结论

优先实施方案 A。

理由：

  1. 符合「先测试、不公开入口」的当前目标。
  2. 数据模型足够简单，一周内可以跑通完整循环。
  3. 归档表的存在已经为未来迁移到方案 B 留下了空间。
  4. 方案 C 的预审机制会显著降低产品趣味，暂不作为首版。

后续迭代方向

  1. 章节浏览：在方案 A 稳定后，把归档页做成可浏览的「往期篇章」。
  2. 预审兜底：如果公共接龙出现 abuse，再引入方案 C 的待审队列作为开关。
  3. 章节主题：迁移到方案 B 的数据模型后，可以推出「限定主题周」，每章一个主题。
  4. 人名池优化：根据 darkroom 记忆的增长，调整人名抽取逻辑和手动保底名单。
  5. 视觉入口：测试完成后，从秘密路径改为固定路由，并考虑放入「关于」或「活动」页面的低调入口。
